# TanStack Query

TanStack Query используется для управления серверным состоянием: загрузкой, кешированием,
повторным получением и изменением данных API. Локальное UI-состояние в Query Cache хранить не
следует.

## Размещение по FSD

| Путь                                | Ответственность                                                      |
| ----------------------------------- | -------------------------------------------------------------------- |
| `src/app/providers/query-provider/` | Подключение `QueryClientProvider` к React-дереву приложения          |
| `src/shared/api/query-client/`      | Создание и получение общего `QueryClient`, глобальные настройки кеша |
| `src/entities/<entity>/api/`        | Query keys, query options и запросы данных конкретной сущности       |
| `src/features/<feature>/api/`       | Мутации и запросы, относящиеся к пользовательскому сценарию          |

Провайдер относится к слою `app`, потому что этот слой собирает приложение и подключает
глобальный React-контекст. Конфигурация клиента не содержит бизнес-логики и доступна нижним
слоям, поэтому находится в `shared/api`. Запросы аутентификации из `AUTH.md` следует размещать
в соответствующих слайсах `features/auth/*/api`, а данные текущего пользователя — в
`entities/user/api`.

## Текущая конфигурация

- На сервере для каждого вызова создаётся новый `QueryClient`, чтобы кеш разных запросов и
  пользователей не пересекался.
- В браузере используется один экземпляр `QueryClient`, чтобы кеш сохранялся между рендерами и
  переходами.
- `staleTime` равен одной минуте. Это предотвращает немедленный повторный запрос на клиенте
  после SSR-гидратации; при необходимости конкретный query может переопределить настройку.
- HTTP-клиент (axios) уже настроен в `shared/api/http-client` — см.
  [`HTTP_CLIENT.md`](HTTP_CLIENT.md). Конкретные `queryFn`, query keys и мутации пока намеренно не
  добавлены: их контракт должен следовать будущей спецификации API.

## Правила расширения

1. Query key объявляется рядом с соответствующей сущностью или фичей, а не в глобальном списке.
2. Повторно используемые query options оформляются через `queryOptions` и экспортируются через
   public API слайса.
3. После успешной мутации затронутые данные обновляются через `setQueryData` или инвалидируются
   по их query key.
4. Для серверного prefetch в App Router используется `getQueryClient`, затем состояние
   передаётся клиентской части через `dehydrate` и `HydrationBoundary`.
5. Ошибки API преобразуются в типизированную прикладную ошибку на границе HTTP-клиента; тексты
   пользовательских сообщений берутся из соответствующего файла в `docs/`.
