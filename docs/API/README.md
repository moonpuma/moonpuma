# API MoonPuma

Инструкция для Codex по составлению запросов к backend API MoonPuma. Первичная версия документа составлена по Swagger-скриншотам backend-команды, переданным 29 июля 2026 года. Полученная из скриншотов информация сохраняется в документе как исходная база, а дальнейшие дополнения и актуализация выполняются согласно [Live Swagger](https://moonpuma.site/api/v1/docs).

## Как использовать этот документ

- Для сетевых контрактов (HTTP-метод, URL, параметры, тело, статус и способ аутентификации) используй этот файл как источник истины.
- При дополнении API-инструкции сверяй новые и изменённые контракты с [Live Swagger](https://moonpuma.site/api/v1/docs), сохраняя ранее зафиксированную по скриншотам информацию, если актуальная спецификация явно её не отменяет.
- Для UI-текстов, клиентской валидации, редиректов и последовательности экранов используй [`../AUTH.md`](../AUTH.md).
- Не придумывай поля ответов или тела ошибок, которых нет в этом документе. Если они нужны для реализации, сначала проверь актуальный Swagger/OpenAPI или уточни контракт у backend-команды.
- Перед изменяющим состояние запросом (`register`, `login`, `logout`, `logout-all`, `refresh-token`, `recover-password`, `change-password`, `confirm`, `google/login`) убедись, что такой запрос входит в задачу пользователя. Не вызывай его только для проверки доступности API.
- Если Swagger/OpenAPI и этот файл расходятся, зафиксируй расхождение и уточни контракт перед реализацией. Не меняй молча ожидаемое поведение.

## Базовые настройки

| Параметр                       | Значение                                                                    |
| ------------------------------ | --------------------------------------------------------------------------- |
| Production base URL            | `https://moonpuma.site/api/v1`                                              |
| Live Swagger                   | `https://moonpuma.site/api/v1/docs`                                         |
| Формат тела запросов           | `application/json`                                                          |
| Аутентификация                 | HttpOnly-cookie `access_token` и `refresh_token`                            |
| Передача токенов из JavaScript | Не читать и не формировать вручную; браузер прикрепляет HttpOnly-cookie сам |

Пути ниже указаны относительно base URL. Например, `POST /auth/login` означает:

```text
POST https://moonpuma.site/api/v1/auth/login
```

Для запросов из браузера, особенно при разных origin frontend и API, передавай cookies:

```ts
await fetch('https://moonpuma.site/api/v1/auth/me', {
  method: 'GET',
  credentials: 'include',
})
```

Для JSON-запросов добавляй `Content-Type: application/json` и сериализуй тело через `JSON.stringify`. У запросов без тела этот заголовок не обязателен.

> Атрибуты cookies (`Domain`, `Path`, `SameSite`, `Secure`, время жизни) и CORS-настройки на скриншотах не показаны. Не фиксируй их в коде на основании предположений.

## Краткая карта endpoint'ов

| Метод  | Путь                          | Назначение                    | Доступ                        |
| ------ | ----------------------------- | ----------------------------- | ----------------------------- |
| `GET`  | `/version-app`                | Версия приложения на стенде   | Публичный                     |
| `POST` | `/auth/register`              | Регистрация                   | Публичный                     |
| `GET`  | `/auth/confirm?code=...`      | Подтверждение email           | Публичный                     |
| `POST` | `/auth/login`                 | Вход по email и паролю        | Публичный                     |
| `GET`  | `/auth/me`                    | Текущий пользователь          | Нужен `access_token`          |
| `POST` | `/auth/refresh-token`         | Обновление пары токенов       | Нужен `refresh_token`         |
| `POST` | `/auth/logout`                | Выход из текущей сессии       | Нужен `access_token`          |
| `POST` | `/auth/logout-all`            | Выход со всех устройств       | Нужен `access_token`          |
| `POST` | `/auth/recover-password`      | Запрос ссылки восстановления  | Публичный                     |
| `POST` | `/auth/change-password`       | Смена пароля по коду          | Публичный, нужен recovery-код |
| `GET`  | `/auth/google/url`            | Получение Google OAuth URL    | Публичный                     |
| `POST` | `/auth/google/login?code=...` | Вход/регистрация через Google | Публичный                     |

## Общие правила обработки ответов

- Успешные ответы `204` не имеют тела. Не вызывай для них `response.json()`.
- Успешные `login`, `google/login` и `refresh-token` возвращают токены через `Set-Cookie`, а не в JSON-теле.
- `401` у защищённых endpoint'ов означает отсутствие, недействительность или просрочку соответствующей cookie.
- `429` означает превышение лимита запросов. Не запускай бесконечные автоматические повторы; учитывай `Retry-After`, если backend его прислал.
- Формат error body на скриншотах не указан. Сначала ветвись по HTTP-статусу, а чтение сообщения делай защитно.
- Для неожиданного статуса сохраняй диагностический контекст (метод, путь, статус), но не логируй пароль, OAuth/recovery-код или содержимое cookies.

Безопасное чтение неизвестного тела ответа:

```ts
const contentType = response.headers.get('content-type')
const payload = contentType?.includes('application/json') ? await response.json() : await response.text()
```

## Endpoint'ы

### `GET /version-app`

Проверяет текущую версию приложения на стенде.

- Параметры: нет.
- Тело запроса: нет.
- `200 application/json`: JSON-строка с версией, например `"string"`.

Не предполагай формат SemVer, пока backend не зафиксирует его отдельно.

### `POST /auth/register`

Создаёт пользователя и отправляет на email письмо со ссылкой подтверждения. Соответствует [`AUTH.md`, UC-1](../AUTH.md#uc-1-регистрация).

Все поля обязательны:

```json
{
  "username": "moon_user",
  "email": "user@example.com",
  "password": "Password1!",
  "passwordConfirmation": "Password1!"
}
```

| Поле                   | Тип      | Ограничения backend-схемы                                                                                                      |
| ---------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `username`             | `string` | Длина `6..30`; только `0-9`, `A-Z`, `a-z`, `_`, `-`                                                                            |
| `email`                | `string` | Валидный email                                                                                                                 |
| `password`             | `string` | Длина `6..20`; минимум одна цифра, одна заглавная и одна строчная латинская буква; допустимы указанные в `AUTH.md` спецсимволы |
| `passwordConfirmation` | `string` | Должен совпадать с `password`                                                                                                  |

Ответы:

| Статус | Значение                                                             |
| ------ | -------------------------------------------------------------------- |
| `201`  | Пользователь создан, письмо с подтверждением отправлено; тело пустое |
| `400`  | Ошибка валидации тела запроса                                        |
| `409`  | Email или имя пользователя уже заняты                                |

### `GET /auth/confirm`

Подтверждает регистрацию по UUID v4 из письма. Соответствует [`AUTH.md`, UC-1, шаги 8–9](../AUTH.md#uc-1-регистрация).

Обязательный query-параметр:

| Параметр | Тип              | Значение                             |
| -------- | ---------------- | ------------------------------------ |
| `code`   | UUID v4 в строке | Код подтверждения из ссылки в письме |

Пример:

```text
GET /auth/confirm?code=00000000-0000-4000-8000-000000000000
```

Ответы:

| Статус | Значение                                                     |
| ------ | ------------------------------------------------------------ |
| `200`  | Email успешно подтверждён                                    |
| `400`  | Код уже использован, просрочен или имеет некорректный формат |
| `404`  | Код подтверждения не найден                                  |

Тело успешного ответа на скриншоте не описано.

### `POST /auth/login`

Выполняет вход по email и паролю. При успехе устанавливает HttpOnly-cookie `access_token` и `refresh_token`; тело ответа пустое. Соответствует [`AUTH.md`, UC-2](../AUTH.md#uc-2-вход-в-систему-log-in).

```json
{
  "email": "user@example.com",
  "password": "Password1!"
}
```

`recaptchaValue` сейчас **не передаётся**: описание endpoint'а сообщает, что reCAPTCHA временно отключена. При этом Swagger-схема `LoginDto` всё ещё показывает `recaptchaValue` как обязательную строку. Это известное расхождение документации; для текущего контракта отправляй только `email` и `password`, а при `400` перепроверь актуальную схему backend.

Ответы:

| Статус | Значение                                                              |
| ------ | --------------------------------------------------------------------- |
| `200`  | Успешный вход; `Set-Cookie: access_token, refresh_token`; тело пустое |
| `400`  | Ошибка валидации тела запроса                                         |
| `401`  | Неверный email или пароль                                             |
| `403`  | reCAPTCHA не пройдена или превышен лимит запросов                     |

### `GET /auth/me`

Возвращает данные авторизованного пользователя по `access_token`.

- Параметры: нет.
- Тело запроса: нет.
- Обязательно отправлять cookies (`credentials: 'include'` в браузере).

Ответы:

| Статус                 | Тело/значение                                 |
| ---------------------- | --------------------------------------------- |
| `200 application/json` | `{ "id": "string" }`                          |
| `401`                  | `access_token` отсутствует или недействителен |

По предоставленной схеме гарантировано только поле `id`. Не закладывайся на наличие `email`, `username` или других полей без обновлённого контракта.

### `POST /auth/refresh-token`

По действительному `refresh_token` из cookie выдаёт новую пару токенов и обновляет cookies `access_token` и `refresh_token`.

- Параметры и тело: нет.
- Обязательно отправлять cookies.

Ответы:

| Статус | Значение                                                  |
| ------ | --------------------------------------------------------- |
| `200`  | Токены обновлены через `Set-Cookie`                       |
| `401`  | `refresh_token` отсутствует, недействителен или просрочен |

Если клиент реализует автоматическое восстановление сессии, допускай не более одного refresh-повтора исходного запроса. Не запускай refresh для самого `/auth/refresh-token` и очищай локальное auth-состояние при его `401`.

**Реализация на клиенте:** уже сделано в `src/shared/api/http-client/http-client.ts` — response-интерцептор `httpClient`. При `401` на любом запросе (кроме самого `/auth/refresh-token`) он один раз помечает запрос `_isRetry`, обновляет токены через `POST /auth/refresh-token` и повторяет исходный запрос; параллельные `401` дедуплицируются в один вызов refresh через общий promise (`refreshRequest`), а не в N параллельных.

Момент «сессия точно истекла» (401 на самом `/auth/refresh-token`, либо неудачный refresh) интерцептор не обрабатывает сам — он не знает про auth-состояние или редиректы, это `shared/api`-слой (см. `CLAUDE.md`, раздел FSD). Вместо этого вызывается колбэк `onSessionExpired`, который app-слой регистрирует через `setOnSessionExpired(callback)` — например, из auth-провайдера при монтировании, где `callback` чистит auth-состояние и редиректит на `/sign-in`. Если колбэк не зарегистрирован, вызов молча пропускается (`onSessionExpired?.()`).

### `POST /auth/logout`

Завершает текущую сессию по `access_token`, отзывает её токены и очищает cookies `access_token` и `refresh_token`. Соответствует [`AUTH.md`, UC-4](../AUTH.md#uc-4-выход-из-системы-log-out).

- Параметры и тело: нет.
- Обязательно отправлять cookies.

Ответы:

| Статус | Значение                                       |
| ------ | ---------------------------------------------- |
| `204`  | Сессия завершена, cookies очищены; тело пустое |
| `401`  | `access_token` отсутствует или недействителен  |

### `POST /auth/logout-all`

Завершает все сессии пользователя, отзывает все его токены и очищает cookies текущего устройства.

- Параметры и тело: нет.
- Обязательно отправлять cookies.

Ответы:

| Статус | Значение                                                               |
| ------ | ---------------------------------------------------------------------- |
| `204`  | Все сессии завершены, cookies текущего устройства очищены; тело пустое |
| `401`  | `access_token` отсутствует или недействителен                          |

Не подменяй этим endpoint'ом обычный выход: `logout-all` влияет на все устройства пользователя.

### `POST /auth/recover-password`

Отправляет письмо со ссылкой и кодом для смены пароля. Соответствует [`AUTH.md`, UC-3, шаги 3–6](../AUTH.md#uc-3-восстановление-пароля-для-front-end-необязательно).

```json
{
  "email": "user@example.com"
}
```

Ответы:

| Статус | Значение                                                      |
| ------ | ------------------------------------------------------------- |
| `200`  | Если email существует, на него отправлено письмо; тело пустое |
| `400`  | Ошибка валидации тела запроса                                 |
| `429`  | Превышен лимит запросов                                       |

Ответ `200` намеренно не раскрывает, зарегистрирован ли email. Не выводи на клиенте сообщение о существовании или отсутствии аккаунта на основании этого ответа.

### `POST /auth/change-password`

Устанавливает новый пароль по recovery-коду из письма. Соответствует [`AUTH.md`, UC-3, шаги 8–12](../AUTH.md#uc-3-восстановление-пароля-для-front-end-необязательно).

Все поля обязательны:

```json
{
  "code": "recovery-code-from-email",
  "password": "NewPassword1!",
  "confirmPassword": "NewPassword1!"
}
```

| Поле              | Тип      | Ограничения                                                                   |
| ----------------- | -------- | ----------------------------------------------------------------------------- |
| `code`            | `string` | Код восстановления из письма; формат на скриншоте не уточнён                  |
| `password`        | `string` | Минимальная длина `6`; применяй полные правила пароля из `AUTH.md` на клиенте |
| `confirmPassword` | `string` | Должен совпадать с `password`                                                 |

Ответы:

| Статус | Значение                                                            |
| ------ | ------------------------------------------------------------------- |
| `204`  | Пароль изменён; тело пустое                                         |
| `400`  | Recovery-код недействителен/просрочен либо тело не прошло валидацию |
| `429`  | Превышен лимит запросов                                             |

Согласно `AUTH.md`, после смены пароля все активные сессии должны быть сброшены.

### `GET /auth/google/url`

Возвращает ссылку на окно согласия Google.

- Параметры и тело: нет.
- `200 application/json`: объект `{ "url": "ссылка" }`.

Пример обработки:

```ts
const response = await fetch('https://moonpuma.site/api/v1/auth/google/url')
const { url } = (await response.json()) as { url: string }

window.location.assign(url)
```

Не конструируй Google OAuth URL самостоятельно.

### `POST /auth/google/login`

Принимает код согласия Google. Если пользователя с таким email нет, создаёт его; затем устанавливает cookies `access_token` и `refresh_token`. Соответствует [`AUTH.md`, UC-5](../AUTH.md#uc-5-регистрация-и-вход-с-помощью-google-или-github-необязательно).

Обязательный query-параметр:

| Параметр | Тип      | Значение                                                    |
| -------- | -------- | ----------------------------------------------------------- |
| `code`   | `string` | Код, полученный после возврата пользователя из Google OAuth |

Код передавай через URL-кодированный query-параметр, не в JSON-теле:

```ts
const url = new URL('https://moonpuma.site/api/v1/auth/google/login')
url.searchParams.set('code', code)

await fetch(url, {
  method: 'POST',
  credentials: 'include',
})
```

Ответы:

| Статус | Значение                                                 |
| ------ | -------------------------------------------------------- |
| `200`  | Успешный вход; `Set-Cookie: access_token, refresh_token` |
| `401`  | Код согласия недействителен                              |
| `429`  | Превышен лимит запросов                                  |

## Рекомендуемый порядок auth-запросов

### Регистрация

1. Проверить поля по правилам `AUTH.md`.
2. Вызвать `POST /auth/register`.
3. На `201` показать сообщение из `AUTH.md`, UC-1, шаг 5.
4. Пользователь переходит по ссылке из письма; код передаётся в `GET /auth/confirm?code=...`.
5. После `200` подтверждения направить пользователя на вход согласно `AUTH.md`, UC-1, шаг 9.

### Вход и восстановление сессии

1. Вызвать `POST /auth/login` с `credentials: 'include'`.
2. На `200` считать вход успешным, не ожидая JSON с токенами.
3. Получить пользователя через `GET /auth/me`.
4. Если защищённый запрос вернул `401`, один раз вызвать `POST /auth/refresh-token` и при успехе один раз повторить исходный запрос.
5. Если refresh вернул `401`, считать сессию завершённой и направить пользователя на вход.

### Google OAuth

1. Получить URL через `GET /auth/google/url`.
2. Перенаправить браузер на полученный `url`.
3. После возврата взять `code` из callback URL.
4. Передать его в `POST /auth/google/login?code=...` с `credentials: 'include'`.
5. На `200` запросить `GET /auth/me` и продолжить как для обычного входа.

### Восстановление пароля

1. Вызвать `POST /auth/recover-password` с email.
2. Независимо от существования аккаунта обработать `200` нейтральным сообщением.
3. Получить recovery-код из ссылки в письме.
4. Вызвать `POST /auth/change-password` с `code`, `password`, `confirmPassword`.
5. На `204` направить пользователя на страницу входа; прежние сессии должны быть недействительны.

## Что ещё не зафиксировано backend-контрактом

Перед реализацией функций, зависящих от этих деталей, запроси актуальный Swagger/OpenAPI или уточнение backend-команды:

- прямой URL OpenAPI JSON/YAML и способ выбора стенда;
- единая структура error body и ошибки по отдельным полям;
- полный объект пользователя из `/auth/me` (сейчас показан только `id`);
- фактическая обязательность и формат `recaptchaValue` после включения reCAPTCHA;
- атрибуты и время жизни auth-cookies;
- наличие CSRF-защиты для cookie-аутентификации;
- CORS и разрешённые frontend origin;
- формат и срок жизни recovery-кода;
- тело успешных ответов `/auth/confirm`, `/auth/google/login` и `/auth/refresh-token`;
- endpoint'ы GitHub OAuth: в `AUTH.md` GitHub упомянут, но на предоставленных API-скриншотах их нет.

## Известные расхождения с проектной документацией

| Тема                                 | Расхождение                                                                                                                                                                                                    | Правило для реализации                                                                             |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| reCAPTCHA при входе                  | `LoginDto` помечает `recaptchaValue` обязательным, но описание `/auth/login` говорит, что reCAPTCHA отключена и поле не передаётся                                                                             | Пока отправлять только `email` и `password`; перед включением reCAPTCHA уточнить контракт          |
| Неизвестный email при восстановлении | `AUTH.md`, UC-3, альтернативный сценарий №1 требует сообщения `{ User with this email doesn't exist }`, но `/auth/recover-password` возвращает одинаковый `200`, только если email существует отправляя письмо | Не пытаться определить существование аккаунта по `200`; согласовать UI-сценарий с backend-командой |
| GitHub OAuth                         | `AUTH.md`, UC-5 описывает Google и GitHub, но API-скриншоты содержат только Google endpoint'ы                                                                                                                  | Не реализовывать GitHub-запросы без дополнительного контракта                                      |
